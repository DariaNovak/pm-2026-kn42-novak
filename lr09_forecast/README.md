## 2. Як рахувалася симуляція

| Поле | Значення |
| --- | --- |
| Інструмент | власний скрипт Python, `lr09_forecast/simulate.py` |
| Прогонів | 10 000, зерно генератора 42 (прогін повторюваний) |
| Що тягнеться випадково | velocity одного зі спринтів історії (`points_done`), з поверненням |
| Як рахується дата прогнозу | останній день спринта, на якому закінчується робота: для сценарію «весь перший реліз» кінець спринта 1 плюс (P − 1) × 14 днів, для сценарію залишку кінець останнього спринта плюс P × 14 днів |

Одна симуляція: беремо обсяг; поки він більший за нуль, `random.choice` тягне
одну velocity з історії, віднімає її від обсягу і додає спринт. Коли обсяг дійшов
до нуля або нижче, записуємо кількість спринтів. 10 000 таких чисел сортуємо;
P50 це найменше число, нижче або на рівні якого лежить 50% результатів, P85 те
саме для 85% (`sorted[ceil(q × N) − 1]`). Результат уже цілий, бо рахуються цілі
спринти, тому округлення вгору виходить саме собою. Захист від нескінченного
циклу: якщо історія складається з самих нулів, цикл обривається на 1000
спринтів.

Запуск:

```bash
python lr09_forecast/simulate.py 220 --csv lr09_reference_velocity.csv
python lr09_forecast/simulate.py 220 --csv lr09_reference_velocity.csv --sprints 1,2
python lr09_forecast/simulate.py 220 --csv lr09_reference_velocity.csv --sprints 5,6
# на власних даних, після спринта 2:
python lr09_forecast/simulate.py 50 --csv lr09_forecast/velocity.csv
python lr09_forecast/simulate.py 32 --csv lr09_forecast/velocity.csv
```

Ядро скрипта:

```python
for _ in range(runs):
    left, sprints = points, 0
    while left > 0:
        left -= rng.choice(history)
        sprints += 1
    results.append(sprints)
results.sort()
p50 = results[math.ceil(0.50 * len(results)) - 1]
p85 = results[math.ceil(0.85 * len(results)) - 1]
```

## 3. Дві дати першого релізу

| Сценарій | Points | P50, спринтів | P85, спринтів | P50, дата | P85, дата |
| --- | :-: | :-: | :-: | :-: | :-: |
| Весь перший реліз | 50 | 6 | 6 | 2027-01-06 | 2027-01-06 |
| Залишок після двох спринтів | 32 (50 − 18) | 4 | 4 | 2027-01-06 | 2027-01-06 |

Дати рахуються за правилом розділу 2: весь реліз 2026-10-28 + (6 − 1) × 14 днів,
залишок 2026-11-11 + 4 × 14 днів. Обидва сценарії дали ту саму дату, і P50
дорівнює P85. Це не означає, що прогноз точний. В історії лише два числа, 8 і
10, тому модель не знає жодного спринта, гіршого за 8. Для залишку в 32 points
три спринти дають щонайбільше 30, а чотири щонайменше 32, тож усі 10 000
прогонів закінчуються на четвертому спринті. Для всього релізу сьомий спринт
потрібен лише тоді, коли всі шість витягнутих спринтів дали по 8 (48 < 50),
тобто в 1/64 ≈ 1,6% прогонів.

Якщо два рядки збіглися до числа, тобто за спринти не закрилось жодної історії
першого релізу: не збіжаться, спринт 1 уже закрив 8 points історій `REL-1`.

Яку з двох дат я вважаю робочою і чому: залишок після двох спринтів. Він
рахує тільки те, що справді лишилось (32 points), а сценарій «весь реліз»
заново розігрує випадково вже закриті спринти, які насправді відомі. Тут дати
збіглися, але при ширшій історії сценарій залишку буде чеснішим. Сума
першого релізу змінилась після ЛР8: 51 → 50 points, бо подія курсу додала S-21
(2), S-22 (3) і +2 до S-01, а S-09 (8) пішла в `REL-2`.
